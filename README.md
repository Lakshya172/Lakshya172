#### [EligiCore](https://github.com/Lakshya172/eligicore)

*Student opportunity eligibility and assisted-application platform.*

EligiCore aims to help students understand which opportunities fit their profiles and move through application preparation with a human checkpoint before final submission. Its design separates resume/profile processing, job ingestion, eligibility, ranking, and application preparation.

- **Structured inputs:** parse resume information into a reusable candidate profile.
- **Explicit decisions:** keep eligibility and recommendation outcomes understandable and testable.
- **Ingestion boundaries:** normalize source records and handle duplicates consistently.
- **Human control:** do not bypass CAPTCHAs or automatically click final submit on third-party sites.
- **Validation-first development:** use automated tests to check rules and edge cases as the project evolves.

**Stack:** Python · API development · data modelling · AI-provider integration · automated tests

**Repository:** [Lakshya172/eligicore ↗](https://github.com/Lakshya172/eligicore)

#### PratiBimb

*Privacy-aware browser-agent safety layer · project design and early-stage work.*

PratiBimb explores how browser automation can handle sensitive information more carefully. The design direction includes typed placeholders for personally identifiable information, explicit verification boundaries, restricted outbound requests, and a memory-only vault concept.

- **Privacy by design:** avoid casually exposing sensitive values to every automation step.
- **Fail-closed verification:** stop when a required safety check cannot be satisfied.
- **Bounded actions:** treat browser actions and outbound requests as policy-controlled operations.
- **Honest project status:** this should be described as an early-stage design until implementation, tests, and measurements are present in the repository.

**Technology direction:** TypeScript · browser automation concepts · ONNX Runtime Web · Playwright · Vitest

A feature is more than the screen where it appears. I’m learning to reason across the full path: the user action, the application rules, the persistence layer, and the integrations that connect the system to the outside world.

### How I think

> A feature isn't finished just because the happy path works.
>
> A rule should be testable.  
> A failure state should be deliberate.  
> Sensitive data should have boundaries.  
> A project claim should match what the code can demonstrate.

- **Make rules explicit.** Business logic should be understandable and testable.
- **Treat edge cases as design work.** Missing data, duplicate records, and invalid states need deliberate behaviour.
- **Separate responsibilities.** Keep API, persistence, and application logic from becoming one tangled layer.
- **Test behaviour, not just execution.** A successful response is not enough if the resulting state is wrong.
- **Describe work honestly.** Distinguish shipped features from experiments, designs, and planned work.
